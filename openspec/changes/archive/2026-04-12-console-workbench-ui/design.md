## Context

当前 Phase 1 前端是一个原生 HTML/CSS/JS 的单页工具，左侧表单用于创建生成任务，右侧以三个独立输出面板展示 `extraction`、`draft`、`rewrite` 结果。现有实现已经具备完整的数据流和实时更新能力，但视觉和信息结构偏展示式：暖色渐变、较重卡片感、并排大块输出区域，会稀释任务状态、阶段进度和当前活跃输出的可扫描性。

这次变更的约束很明确：
- 保持现有后端 API、SSE 事件和任务流程不变
- 保持原生前端技术栈，不以引入框架作为改造前提
- 在不增加交互复杂度的前提下，把页面重构为更接近控制台 / 工作台的操作界面

## Goals / Non-Goals

**Goals:**
- 让用户能够在单页内快速识别当前任务、阶段状态和活跃输出
- 将输入区域重构为紧凑的控制面板，减少视觉装饰对操作的干扰
- 将三阶段输出重构为流水线监控 + 聚焦查看模式，降低同时阅读多块长文本的负担
- 在桌面端形成稳定的工作台分区，在窄屏场景下保持相同信息优先级

**Non-Goals:**
- 不引入 React、Vue 或新的 CSS 框架
- 不改变任务创建、任务查询或 SSE 协议
- 不新增历史会话管理、输出编辑器或文档导出能力
- 不重新设计后端阶段定义，仍然围绕 `extraction`、`draft`、`rewrite`

## Decisions

### 1. 采用“双栏工作台 + 顶部状态栏”布局

页面将改为三层结构：
- 顶部固定或高可见状态栏，展示 session、task、总体状态和当前阶段
- 左栏为控制面板，容纳表单、主操作按钮和简要说明
- 右栏为任务工作区，包含流水线阶段条与聚焦输出区

这样做的原因是当前页面最核心的操作链路就是“配置参数 -> 启动任务 -> 观察阶段 -> 阅读结果”。把状态栏从内容区抽离，可以减少用户在页面中搜索任务状态的成本。

替代方案：
- 保持现有双卡片布局，仅调轻颜色和圆角。放弃该方案，因为它只能降低“花哨感”，不能解决信息组织问题。
- 改成单栏纵向布局。放弃该方案，因为桌面端会拉长视线移动路径，不利于高频观察。

### 2. 将三阶段输出从并列大面板改为“阶段监控 + 单主输出”

右侧工作区采用“阶段概览 + 当前查看内容”的模式：
- 阶段概览始终可见，展示每个阶段的状态
- 主输出区一次聚焦一个阶段内容，默认优先显示当前活跃阶段，完成后优先显示最终 `rewrite`
- 用户仍可切换查看其他阶段，避免丢失中间结果

这样做的原因是 streaming 场景下用户更关心“现在跑到哪里”和“当前输出是什么”，而不是同时阅读三块长文本。单主输出能提升可读性，也为后续加入复制、差异对比等操作保留空间。

替代方案：
- 三个输出面板继续同时展示，只做高度和样式压缩。放弃该方案，因为长文本并排仍然会造成注意力分散。

### 3. 视觉语言改为中性、低装饰、状态驱动

样式层采用以下方向：
- 使用中性浅色背景和细分隔线替代暖色渐变与重阴影
- 减少大圆角与胶囊按钮，改为更克制的组件轮廓
- 用颜色区分状态，而不是制造氛围
- 保留输出区较高对比度，但避免与页面其余部分形成过强风格割裂

这样做的原因是“效率优先”不等于去样式，而是让样式服务于扫描效率。状态色只用于 `idle / pending / running / done / failed` 等核心反馈，用户对界面的理解会更直接。

替代方案：
- 极端终端化的黑底控制台风格。放弃该方案，因为该产品面向文书生成场景，过强的工程师终端隐喻会降低通用性和阅读舒适度。

### 4. 保持现有事件流，前端只增加轻量视图状态

现有 `generation-form.js` 已经维护了按钮状态、任务状态和分阶段内容追加逻辑。改造时只需要增加轻量级前端视图状态，例如：
- 当前选中的阶段
- 当前活跃阶段
- 是否已有最终结果可优先显示

这保证重构主要聚焦于界面组织，而不是重写事件模型或引入新的状态管理模式。

替代方案：
- 借机引入组件框架统一状态管理。放弃该方案，因为当前复杂度不足以支撑框架迁移成本。

## Risks / Trade-offs

- [用户习惯三栏同时查看] → 保留阶段切换入口，并确保各阶段内容不会因聚焦视图而丢失
- [状态信息过度压缩导致字段不清晰] → 顶部状态栏仅保留 task、session、status、stage 四类核心信息
- [重构 HTML 结构可能影响现有 JS 选择器] → 保持关键 DOM id 稳定，优先在结构外围扩展，而不是直接改写已有数据绑定点
- [移动端空间有限] → 在窄屏下回退为纵向工作台，但保持“状态栏优先、主输出优先”的信息顺序

## Migration Plan

1. 重构页面骨架和语义分区，但保留现有表单字段与输出节点 id
2. 更新样式变量、布局系统和状态视觉规范
3. 增加阶段聚焦查看逻辑，并与现有流式事件对接
4. 用本地手动验证和现有前端测试确认提交、流式更新和完成态仍然正常

回滚策略：
- 该改造局限于前端静态资源，可通过回退 `frontend/` 目录相关文件恢复旧界面

## Open Questions

- 是否需要在控制面板内加入预设模板入口，还是先保持纯表单
- 最终输出区是否需要额外提供复制按钮，还是留待后续迭代
- 移动端是否只要求可用，还是也要尽量保留桌面端的工作台感
