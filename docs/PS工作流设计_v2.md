# PS 工作流设计 v2

本文档用于固化当前已经确认的 Personal Statement（PS）生成工作流，作为后续产品设计、OpenSpec proposal 和工程实现的基础。

当前范围明确如下：

- 本项目当前只聚焦 `Personal Statement (PS)`
- 支持生成 `中文` 或 `英文` 版本
- 工作流核心不是“直接写成稿”，而是“先确认论证框架，再生成正文”

---

## 1. 工作流目标

新版工作流的目标是：

- 先把 PS 的论证框架搭对
- 再让用户编辑和确认框架
- 最后基于确认版框架生成正文

这个工作流默认承认以下判断：

- 文书最大的问题通常不是缺素材，而是缺主线和逻辑
- 用户真正最需要控制的是 outline，而不是最终措辞
- AI 应先产出一个可编辑的论证蓝图，而不是直接输出整篇成稿

---

## 2. 总体流程

确认后的目标工作流如下：

```text
原始资料
  ↓
1. extraction
  ↓
2. outline draft（AI 起草，中文输出）
  ↓
3. user edit + confirm
  用户编辑 outline
  用户可填写“下一步生成备注”
  用户选择输出语言：中文 / 英文
  ↓
4. draft
  基于确认版 outline 生成正文初稿
  对 outline 采取弱约束
  ↓
5. rewrite
  优化语言、衔接和人味
  严禁重构 outline
  ↓
6. fact-check
  ↓
7. repair（如需要）
```

---

## 3. 各阶段职责

### 3.1 extraction

职责：

- 从原始输入材料中抽取结构化事实
- 形成后续所有阶段共享的 profile
- 为后续 outline 提供可靠的事实边界

这一阶段只解决：

- 学生做过什么
- 申请目标是什么
- 哪些信息明确存在
- 哪些信息不能编造

这一阶段不负责：

- 决定文章主线
- 决定段落结构
- 决定语言风格

### 3.2 outline draft

职责：

- 由 AI 基于 extraction 结果起草一份 PS 论证蓝图
- 默认使用中文输出，便于用户快速判断和编辑
- 先解决“这篇文章要怎么组织”，再进入写作

这一阶段是整个工作流的核心控制点。

outline draft 的目标不是生成成文，而是生成一个可编辑的结构方案，至少应覆盖：

- 申请学校 / 项目
- PS 主线主题
- 开头方向
- 2 到 3 个核心论点
- 每个论点对应的支撑经历
- 结尾回扣方向
- 风险点或不应写入的内容

### 3.3 user edit + confirm

职责：

- 用户对 AI 起草的 outline 进行完整编辑
- 用户确认文章真正要采用的论证结构
- 用户可附加下一步生成备注
- 用户在此时选择输出语言：中文 / 英文

这里的产品定位不是“让用户点确认”，而是“让用户真正控制框架”。

可编辑范围应尽可能充分，包括但不限于：

- 修改主线主题
- 修改论点标题或表述
- 删除某个论点
- 调整论点顺序
- 增删某个论点下的支撑经历
- 标记某些内容不要写
- 增加下一步生成备注

确认后的 outline 应被视为后续正文生成的核心依据。

### 3.4 draft

职责：

- 基于确认版 outline 生成完整 PS 初稿
- 按用户选定语言生成中文或英文版本
- 将论证蓝图展开成自然文章

这一阶段对 outline 采取“弱约束”。

弱约束的含义是：

- 可以为了文章流畅度补充过渡
- 可以调整段内句子顺序
- 可以在不改变论点的前提下微调展开比例
- 可以调整段落长短

但不允许：

- 新增核心论点
- 删除已确认核心论点
- 改变论点要证明的内容
- 改写成与已确认 outline 不同的主线

一句话总结：

- draft 可以优化“怎么说”
- draft 不能改动“要说什么”

### 3.5 rewrite

职责：

- 提升语言质量
- 优化段落衔接
- 增强自然度和人类表达感
- 去掉明显 AI 腔

这一阶段采取“强约束”。

rewrite 严格禁止：

- 重构 outline
- 改变核心论点
- 改变段落职责
- 改变结尾回扣关系
- 引入新的主线

rewrite 可以做的事情包括：

- 调整措辞
- 优化句式
- 增强自然过渡
- 提升语气一致性
- 提升可读性

一句话总结：

- rewrite 只优化成文质量
- rewrite 不重新设计文章结构

### 3.6 fact-check

职责：

- 检查最终文本是否超出资料边界
- 检查是否缺少必要硬性元素
- 检查是否出现不该出现的具体事实

这一阶段主要解决：

- 事实越界
- 关键字段遗漏
- school-specific 内容编造
- 重要真实事实锚点缺失

### 3.7 repair

职责：

- 当 fact-check 未通过时，对最终稿做修复
- 优先修复事实正确性和硬性要求缺失

repair 属于兜底环节，不是主表达环节。

## 4. 语言分流策略

当前已确认的语言策略如下：

- 项目只做 PS，不在文书类型上继续扩散
- 语言分为 `中文` 和 `英文`
- outline 默认使用中文生成和编辑
- 用户在确认 outline 时再选择最终输出语言

建议的阶段分流方式：

- `extraction`：中英文共用
- `outline draft`：共用逻辑，默认中文输出
- `user edit + confirm`：共用
- `draft`：按语言分为中文 draft 和英文 draft
- `rewrite`：按语言分为中文 rewrite 和英文 rewrite
- `fact-check`：规则基本共用，输出格式可统一

这样做的好处是：

- 前半段聚焦结构控制
- 后半段聚焦语言表达
- 同一份确认版 outline 可复用于中英文两个版本

## 5. 核心设计原则

### 5.1 先确认结构，再生成正文

系统不应直接从原始资料跳到最终文书。
系统应先生成一份可编辑的 outline，并让用户确认。

### 5.2 outline 是整个工作流的核心资产

在这个工作流里，真正最重要的中间对象不是 draft essay，而是 confirmed outline。

因为：

- profile 解决事实边界
- outline 解决论证结构
- essay 只是把 outline 展开成成文

### 5.3 用户控制框架，AI负责展开

AI 负责起草框架和生成文本。
用户负责确认文章真正的主线、论点和材料取舍。

### 5.4 draft 弱约束，rewrite 强约束

这条原则已经明确确认：

- `draft` 可以在不改变 outline 的前提下做柔性展开
- `rewrite` 不能再改变 outline

### 5.5 工作流优先解决逻辑问题，再解决文风问题

当前产品最应优先控制的是：

- 主线是否正确
- 论点是否成立
- 事实是否映射得当
- 结构是否完整

语言“像不像人写的”属于重要但靠后的优化层。

---

## 6. 业务状态流建议

相比简单记录当前 stage，更适合当前业务的状态流可以是：

```text
session created
  ↓
profile ready
  ↓
outline drafted
  ↓
outline edited
  ↓
outline confirmed
  ↓
draft generated
  ↓
rewrite completed
  ↓
fact-check passed / needs repair
```

这条状态流更贴近真实业务过程，因为它把“outline 是否已确认”作为核心节点。

---

## 7. 当前版本的结论

当前确认的 PS 工作流可以概括为一句话：

先让 AI 起草一份中文 outline，由用户充分编辑并确认，再基于确认版 outline 和用户选择的语言生成正文，其中 draft 可做弱约束展开，rewrite 严格禁止重构 outline。

这是后续产品设计和工程实现的基准版本。
